# 设计请求：多语言词典的数据形态

> 本文是一次对外征询，欢迎直接评论 / 逐条回答第 6 节的问题。作者对多语言 l10n 工程化没有长期实践经验，下面的候选方案与倾向都可能选错。

## 1. 一句话问题

一个**键会随上游改版频繁变动**的词典，要装下 N 种语言，数据该怎么摆——才能既不让「上游改一个字符串」变成「N 个文件都要动」，又不引入更糟的失效模式？

## 2. 背景（自足，不需要了解本仓库）

### 2.1 项目与工作方式

浏览器扩展（Chrome / Edge，MV3），把 GitHub 界面译成目标语言。工作方式是**本地静态替换，无网络请求**：

- **键** = GitHub 实际渲染的**英文原文文本节点**（「整节点精确匹配」语义，例如 `Pull requests`、`Collaborators 3`）。
- **值** = 目标语言译文；命中的节点被就地替换。
- 另有 **207 条正则规则**处理动态文本（相对时间、计数），`pattern` 对整段已 trim 文本 test，首条命中生效——**规则顺序是语义的一部分**。
- 键**不是**开发者手写的 i18n key，而是用「开发者模式」在真机上**采集**漏翻文本得到的：逛页面 → 收集未命中文本 → 批量补进词典。也就是说，键的身份天生就是那段英文本身，没有人工命名的中间层。

### 2.2 现状规模

| 项 | 数量 |
| --- | --- |
| 静态词条键 | 1618 |
| 正则规则 | 207 |
| 页面模块 | 15（按路由拆分，另有 1 个全站模块） |
| 目标语言 | 现在 1 种（简体中文），计划 N 种 |
| content.js 产物 | 约 165 KB（含全部中文词典） |

现状是**每 locale 一份数据的单语言结构**：`data/global.jsonc` + `data/pages/<页名>.jsonc`，形状是扁平的 `键 → 译文`，JSONC（带注释），顶部有 `$schema` 指向一份 JSON Schema 做编辑器校验。

### 2.3 两类数据的变更频率完全不同（这是问题的根源）

| | 键（英文原文） | 译文 |
| --- | --- | --- |
| 因何而变 | 上游改版（GitHub 正在渐进迁移 React 重写页面，节点结构/文案都会变） | 译者修订 |
| 变更频率 | 高，且**不可预期** | 低 |
| 谁改 | 维护者，一次性横跨所有语言 | 各语言贡献者，互相独立 |
| 失效方式 | 静默：键失配 → 那条不再翻译，不报错、CI 全绿 | 通常可见 |
| 数量级 | 1618 个键共享一个「当前正确值」 | 每个 locale 一份 |

真实的例子（摘自本项目提交历史）：上游把 `Collaborators 3` 从单个文本节点拆成 `<span>Collaborators</span><span>3</span>`，原键永久失配，必须新增词条才能恢复翻译。**这类改动与语言无关，却要求每个 locale 都重新提供一次译文。**

## 3. 什么算「优雅」——可检验的判据

不想只凭感觉争论，先把判据列出来，欢迎补充：

1. **上游改一个键，需要编辑的文件数**（希望接近 1；至少是可脚本化的）。
2. **上游改一个键，是否需要每个 locale 重译**（希望不需要——若语义未变，只是文案/节点变了）。
3. **缺失译文的可见性**：某个 locale 缺了哪些键，能否机械地列出并在编辑器/CI 里报出来。
4. **社区贡献者并行度**：不同语言的贡献者同时提 PR，会不会改到同一行（合并冲突）。
5. **diff 可读性**：一次「上游改版」的 PR 应该只动键相关的内容；一次「日语翻译」的 PR 应该只动日语文件。
6. **门禁可验证性**：键集合、译文合法性、防循环约束（见 5.2）能否在 CI 里断言。
7. **包体增长**：N 种语言全量打进 content script，还是按 locale 分发。

## 4. 候选方案

### A. 每 locale 一个目录（键重复 N 份）

```
data/zh-CN/pages/issues.jsonc   { "entries": { "Pull requests": "拉取请求" } }
data/ja/pages/issues.jsonc      { "entries": { "Pull requests": "プルリクエスト" } }
```

- ✅ 贡献者并行度最好：日语 PR 只碰 `data/ja/**`，与中文、与键更新都不冲突（判据 4、5）
- ✅ 每个文件是独立完整的语言包，便于按 locale 打包（判据 7）
- ✅ 缺译文 = 缺键。可以用门禁直接算覆盖率（判据 3）
- ⚠️ 键重复 N 份（判据 1）。但**漂移可机械检出**：门禁断言「各 locale 键集合一致」，或反过来把「不一致」当作覆盖率信号
- ⚠️ 需要配套的传播工具：键增删时同步到 N 个文件，新增键留空并标记待译
- ⚠️ 「每个 locale 都要重译」的问题它解决不了（判据 2）

### B. 同一文件内嵌套译文（键只有一份）

```jsonc
"entries": {
  "Pull requests": { "zh-CN": "拉取请求", "ja": "プルリクエスト" }
}
```

- ✅ 键单点维护（判据 1、2 最好）
- ✅ $schema 可以直接对「缺哪个语言」报编辑器红线（判据 3）
- ❌ **不同语言的贡献者会改到同一行**（判据 4、5）——两个译者同时改 `Pull requests` 的 `ja` 与 `zh-CN`，同文件同行冲突
- ❌ 每一行都被对象包一层，行宽/代码量 N 倍，diff 噪音明显
- ❌ 键更新仍要动 N 个值（只是同一文件内），实际是「一处文件、N 处编辑」

### C. 稳定 ID：键注册表 + 每 locale 覆盖

```
data/keys/pages-issues.jsonc  { "issues.list.pull_requests": { "source": "Pull requests" } }
data/zh-CN.jsonc              { "issues.list.pull_requests": "拉取请求" }
data/ja.jsonc                 { "issues.list.pull_requests": "プルリクエスト" }
```

- ✅ **上游改文案只改注册表里 `source` 一行，译文完全不受影响**（判据 1、2 都做到 O(1)）
- ✅ 各 locale 文件按 ID 覆盖，冲突少（判据 4）
- ❌ **1618 个 ID 需要人命名与维护**：本项目的工作方式是「实机采集 → 粘贴补录」，采集到一条就得给它起个语义 ID（`issues.list.pull_requests`？`issues_tab.pullRequests`？），这是给一条流水线作业硬塞一道人工命名工序
- ❌ 审阅译文时看不到英文原文（除非在 locale 文件里带注释，那又变成键重复）
- ❌ 新失效模式：ID 没变但语义变了 → 静默沿用旧译文
- ❌ ID 命名本身就是长期 bikeshedding 来源

### D. PO / 翻译记忆式：键即原文，每 locale 稀疏覆盖 + 迁移工具

```
data/zh-CN/pages/issues.jsonc   { "entries": { "Pull requests": "拉取请求" } }   // 只列已译键
data/ja/pages/issues.jsonc      { "entries": { /* 未译则缺键，引擎回退英文 */ } }
```

关键点：**引擎已有「未命中即保持英文」的行为，所以「某 locale 缺键」不是错误，而是「尚未翻译」**。因此判据 3 里担心的「键集合漂移」其实不是问题——各 locale 的键集合本来就不需要相同。

于是真正剩下的问题变成：**上游改键之后，旧键上的译文怎么迁移到新键。** 这是 l10n 领域的老问题，标准解法是 `msgmerge` 式的模糊匹配：把旧译文按相似度迁到新键，并标记为 `fuzzy` 待人工确认。

- ✅ 键单点（按语言各一份，但只有已译的才出现）
- ✅ 无「键集合必须一致」的硬约束
- ⚠️ 上游改键仍是 N 处编辑，但可以用**一个共享的迁移映射**驱动 codemod；甚至可以在运行时支持别名，做到「加一行别名，N 个 locale 都不用动」
- ⚠️ 死键（上游已不再渲染）会静默堆积，需要清理机制

### 4.1 一条独立建议：规则不要跟着条目走

207 条规则里，**`pattern` 与语言无关，只有 `replacement` 与语言有关**；而**规则顺序是语义**（首条命中生效）。若把规则按 locale 拆成 N 份，就必须保证 N 份的顺序永远一致，这是个新的同步负担。

建议：**规则留在一个共享文件里，只有 `replacement` 按 locale 嵌套**；条目按 A/B/D 之一走。条目 1618 条要防冲突，规则 207 条要保顺序，两类数据的诉求正好相反。

## 5. 其他相关但独立的设计点

### 5.1 目标语言的选择与扩展自身 UI

扩展名 / 描述 / popup 文案目前硬编码中文，计划改成中性名 + `_locales` + `__MSG_*__`。顺带记录一个坑：现有实机探针靠 `chrome.runtime.getManifest().name` 匹配扩展上下文，一旦 name 走 `__MSG_`，该值会随浏览器语言变化，探针的身份识别会失效。

### 5.2 防循环守卫目前是「中文专用」的，必须一起改

译文必须含汉字（`\p{Script=Han}`）这条约束现在同时承担两件事：**（a）门禁校验译文合法性；（b）防止翻译循环**——替换后文本若仍「可翻译」，观察器会再翻一遍。

我把循环的真实条件推了一遍：需要同时满足「脚本守卫没拦住译文」**且**「译文本身又是一个词典键、或能命中某条规则」。所以：

- 中文今天安全，纯属脚本守卫挡住了第二遍。
- 日语：含汉字的译文能过，**纯假名译文（「もっと見る」）会被门禁拒绝**。
- 韩语 / 泰语 / 阿拉伯语：守卫完全失效，门禁拒绝一切。
- 西 / 法 / 德（拉丁字母）：守卫**结构上不可能生效**。

因此我倾向的持久修法不是「每种语言写一个脚本判断」，而是**从结构上让第二个条件不可能发生**，并把它做成与语言无关的门禁：**任何 locale 的译文都不得等于任何词典键**（外加规则产物的再命中检查）。这样各语言拿到同一套保证。这一条与数据形状耦合——门禁要拿到「键集合」，而形状决定了它好不好拿。

## 7. 附：现状事实清单

- 数据文件：`src/dict/data/global.jsonc`（全站，314 键 / 73 规则）+ `src/dict/data/pages/<页名>.jsonc`（15 个页面模块）
- 形状：扁平 `键 → 译文`；规则为 `{ pattern, replacement }` 数组；JSONC 支持注释，现有 245 行分组注释是有意保留的维护信息
- 校验：`src/dict/dict.schema.json`（编辑器侧 JSON Schema）+ `bun run check:dict`（CI 门禁：结构编译、键值合法性、脚本/CJK 约束）
- 加载：`src/dict/load.ts` 把字符串正则编译成 `RegExp`；`src/dict/registry.ts` 定义模块顺序（顺序即优先级，存在 5 处**有意的**跨模块同键异译，靠顺序生效）
- 探针：`bun run verify` 用无头浏览器加载扩展、逐页采集漏翻并导出 JSON；目前「是否翻译生效」的判据硬编码了中文词（`zhSignUp` / `zhSignIn`）与 CJK 计数
- 迁移历史：词典刚从 TS 模块迁到 JSONC（为了编辑器校验、批量追加安全、重复键由 Biome 覆盖），并做了「迁移前后最终合并视图 SHA256 完全一致」的等价性验证

## 8. 结论：已实施（本轮落地）

本节是事后补记。上面列出的 4 种候选里**采纳 D（键即原文 + 每 locale 稀疏覆盖）**，并吸收了评审建议；实施结果与本文的推测有出入的地方以本节为准。落地提交见 `feat(i18n)` / `refactor(dict)` 系列。

实际形态：

```
src/dict/
├── core/                          # 语言无关，每个语言共享一份
│   ├── modules.jsonc              # 模块名 + 路由（顺序即优先级，global 兜底在最后）
│   ├── rules.jsonc                # 规则 id + pattern（顺序即语义）
│   ├── aliases.jsonc              # 上游改名映射：当前 DOM 文本 → 规范键
│   └── canonical.jsonc            # 规范键清单（仅门禁使用，不进 content 包）
└── locales/<语言 id>/             # 只有译文，稀疏覆盖（缺模块/键/模板 = 未翻译）
    ├── global.jsonc + pages/<页名>.jsonc
    └── rules.jsonc                # 规则 id → 替换模板
```

与本文推测的差异，都是实施时才看清的：

1. **规则必须保留模块作用域**。本文只说了「pattern 共享、replacement 按语言拆」，但没提规则也受路由限制（`pages/issues` 的规则只在议题页生效）。故 `core/rules.jsonc` 按模块分组，且分组顺序必须与 `core/modules.jsonc` 一致（门禁强制）。
2. **规则需要 id，且 id 是维护者命名**。要让「上游改 pattern」保持 O(1)，语言侧的模板必须靠稳定 id 对齐（用 pattern 文本当键会让改 pattern 变成 N 处编辑）。本轮为 207 条规则一次性命名，id 形如 `global/minutes-ago`。
3. **canonical 是身份，不是「当前渲染文本」的快照**。上游改词时优先保住已有译文的键身份，用 aliases 吸收 DOM 文本漂移（这样才是 O(1)）；只有语义变了才改名并重译。拼错键从此会报错，而不是像旧形态那样静默不翻。
4. **覆盖率的分母只能是 canonical**。若用「各语言键集合的并集」当分母，一个谁都没译的键就会凭空消失。代价是 canonical 里会积累上游已删除的死键（不报错），靠实机探针定期清理。
5. **`core/canonical.jsonc` 不进包**。它只被门禁 import，1618 个键约 20 KB 不进 content.js。

实测数字（本文第 2 节与第 7 节的数字是迁移前的）：

| 项 | 迁移前 | 迁移后 |
| --- | --- | --- |
| 词条 / 规则 / 模块 | 1618 / 207 / 16 | 同（zh-CN 完整，ja 样例 50 词条 / 7 模板） |
| 数据紧凑 JSON | 131218 字节（实测口径：entries + rules） | 144273 字节（含规则 id、模块名、别名表） |
| content.js | 168616 字节 | 194649 字节（`minify: false`） |
| 迁移等价性 | — | 27 条路径的合并视图 SHA256 逐字节相同（`7f6a2891…9d8a5c`） |

第 6 节的两个问题，本轮给出的答案：

- **复数语法分歧**（俄语 / 阿拉伯语）**确实是当前形态的边界**：一个 pattern 只能配一个模板，没有复数类别。要支持得引入 `Intl.PluralRules` 式的多模板，本轮不做。
- **包体策略**：N=2 维持全量打包（同步注入、无闪烁）；数据仍是大头（约 74%），N≥4 时再评估按 locale 分发。
